## Resolved 2026-10-15: the live site can take a payment again

This file led, for two days, with the live site being unable to take a
payment. `checkouts:write` and `customer_sessions:write` are now on the
`Euclid-Production` token and the 502s are gone. Verified from the app's side
rather than from the dashboard's toast: a POST with a deliberately bogus id
answers **422** for both scopes, where it answered 403 before. No redeploy was
needed, because the token's value never changed — only its scopes.

The original two traps, with the second one corrected now that it is
understood:

- **`checkout_links:write` is not `checkouts:write`.** They sit a few rows
  apart and differ by one word. The wrong one had been ticked, along with
  `benefits:write`; both were removed later the same day, leaving exactly the
  six below. Probed after: the two the app needs answer 422, the two removed
  answer 403.
- **The re-auth is a full-page redirect, not a modal.** This was written down
  as "the modal discards the form", which put the blame in the wrong place and
  made the problem look unavoidable. Confirming navigates the whole tab to
  `polar.sh/auth?return_to=…`, and the half-filled form dies with the page.
  So **signing in first does help** — the earlier note said it did not. With a
  fresh session the prompt never fires and the update saves on the first
  attempt. Creating a new token was never necessary.

The six scopes this app wants: `checkouts:write`, `customer_sessions:write`,
`products:read`, `discounts:read`, `webhooks:read`, `orders:read`. Everything
else, especially anything that can move money, should stay off a token that
lives in Vercel's environment.

## Done

### Browser end-to-end tests

14 Playwright specs in `tests/e2e`, running in CI as the last steps of the
integration job — the same local Supabase and built app, so it cost four steps
rather than a second environment.

They found two real bugs on the first run, both invisible to anything that
does not open a page:

- **Escape never closed the floating widget.** The loader focuses the iframe
  on open, so keypresses landed in the frame's document and the host page's
  handler never heard them. Fixed by posting `euclid:close` to the parent.
- **Inline mode mounted in the wrong place.** `mountInline()` put the host
  element in the founder's container and an unconditional
  `documentElement.appendChild` moved it straight back out.

### Email retries no longer wait for the scheduler

`0015_email_retry`. `email_outbox` had no `attempts`, `deliver_after` or
`last_error`, so a failed send sat there until the daily cron — and a magic
link expires in an hour. Claiming is now atomic, which also closed a
duplicate-send bug: `drainAfterResponse` fires on every post and publish, and
two overlapping requests could both send the same row.

This removed the need for a more frequent cron, so **Vercel Pro is not
required** for anything.

### AI cost

Measured rather than guessed — the app recorded no token usage at all before
this, which is why two earlier estimates were wrong by ~7x in opposite
directions.

- `MODEL_STRONG` is **Sonnet 5**, not Opus 5. A true drop-in.
- **Prompt caching** in the two places a prefix is actually re-sent: the chat
  agent's loop and Build Prompt refinements. Nowhere else — the other call
  sites are single requests with ~270-token system prompts, under the
  ~1024-token minimum, where a breakpoint would cache nothing while looking
  like it worked.
- Usage lines in `askEuclid` and `generateDraft` are now the only record of
  what any of it costs.

Measured: a chat question went **$0.167 → $0.071**; a repeat Build Prompt
generation now pays for *two* input tokens. Output is ~85% of what is left, so
the next saving is shorter outputs, not more caching.

### Found while cancelling the test trial, 2026-10-15

Neither of these blocks anything today, but both are wrong in front of a
paying founder.

- **A cancelled subscription looks active in the app.** Cancelling through the
  customer portal sets Polar's subscription to expire at period end, and Polar
  keeps `status` as `trialing`/`active` while it runs out. The webhook handler
  reads only `status` (`src/app/api/billing/webhook/route.ts:161-176`), so
  nothing in `workspaces` changes and the billing page still shows **Active**
  with a "Cancel subscription" button. A founder who cancels gets no
  acknowledgement and is still told they will be charged again. The signal
  Polar sends but the app ignores is the cancel-at-period-end flag; it needs a
  column and a line in the handler.
- **The "renews" date is the wrong date.** `billing-view.tsx:97-98` computes it
  as `periodStart + 1 month`, where `periodStart` is the *usage* period start —
  the allowance reset — not the billing period end. On the test workspace the
  header said "renews November 1, 2026" while the banner directly below it
  said the period runs to 10/22/2026. Two dates, one screen, and the one
  labelled "renews" is the one that is not the renewal.

## Things that cost time, so they are written down

- **An unsubscribed webhook event is never sent.** The first top-up purchase
  granted nothing because `order.paid` was not ticked on the endpoint. The
  checkout completed, the card was charged, and *no request reached the
  server* — nothing in the app could have explained it.
- **A new webhook endpoint defaults to API version `2026-10`** while the app
  imports the `2027-01` SDK. Field names differ. Patched, but check it on any
  endpoint created later.
- **Synthetic clicks do not reach Polar's form state.** A scripted `.click()`
  flips `aria-checked` and the hidden input, and Save then writes the *old*
  set back. Real clicks at screenshot coordinates are the only reliable way —
  and `getBoundingClientRect` disagrees with screenshot pixels, because the
  viewport is 1920 wide while screenshots are 1568.
- **Polar rejects reserved e-mail domains.** `@euclid.test` fails as "a
  special-use or reserved name", and that address reaches Polar as
  `customer_email` straight from the signed-in founder. Test accounts that
  touch a real checkout need a normal domain.
- **A bogus id is the cheapest permission probe.** 403 means the scope is
  absent; 404 or 422 means the scope is there and only the id was wrong. That
  is how both missing scopes were isolated without creating anything, and on
  2026-10-15 how the fix was confirmed without taking a payment to find out.
- **Next's `Link` cannot follow an off-origin redirect.** The top-up buttons
  shipped dead because of it; the billing routes need
  `window.location.assign`. The codebase already said so on the upgrade
  button.
